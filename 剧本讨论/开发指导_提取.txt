一、游戏概览与核心循环
1.1 游戏简介
《光轨》是一款以“北航Wota艺社团重建”为主题的周次制文字养成游戏。玩家扮演一名大一新生，在20周内通过选择地点行动学习技能、积累知名度、触发剧情，最终影响社团走向及个人故事结局。
2025年秋，飞梦ACG联盟元气大伤，其下属宅艺研仅剩最后一名成员林若。你在高考后的暑假通过B站第一次接触Wota艺。荧光棒在黑暗中划出光弧的姿态让你看到了梦想中大学的自己。来北航之前你就查好了宅艺研的信息，你不知道的是，等你到的时候，那个社团已经面临废社。
1.2 每周执行流程
选择地点 → 地点简短反馈(固定文本) → 触发固定周目剧情(若有) → 数值判定，检查是否满足判定触发剧情条件
每周循环一次，20次循环后游戏进入结局判定。特定事件（如厄介结局）可能提前终止游戏。

1.4 角色档案
主角（你）：北航大一新生。高考后暑假在B站第一次看到Wota艺视频，在阳台上独自练习了两个月。来北航就是为了找到打Wota艺的人。你不是天赋型选手，很多爱好也曾半途而废，但Wota社让你找到了社团活动是什么感觉。
林若：北航大二工科生，焲痕Wota社现任社长。原飞梦ACG联盟宅艺研最后一名留守成员。对技艺有近乎偏执的追求，逐帧回放练习视频挑刺，同一段技反复打三十遍直到“光轨没有瑕疵”。她的偏执源于误解，她以为宋柯是因为她技术不够才离开的。
宋柯：北航大三工科生。前宅艺研成员，林若的入门恩师。现于学校附近“回声Livehouse”担任兼职灯光师。早年在地偶现场的应援视频被扒出后遭受网暴，留下“我从未觉得打艺开心过”后离开。他说“至少灯光不会被人截图分析”。
叶子：主角的幼驯染。两人从小一起长大，考进同一所大学。她十八年来一直在做“正确”的事，却从没做过一件想做的事。她不了解ACG，不知道Bメロ是什么意思，第一次看到荧光棒时问电池能用多久。她帮社团跑行政申请不是因为对Wota艺感兴趣，而是因为你在打艺时的专注神情，是她在自己身上从未见过的。
夜凪：瘦高个男生，学院路校区学生。高中打过两年艺，原社团在高考那年解散。网名“夜凪”（やなぎ），寓意“风停在夜里”。他在B站看到焲痕社的视频后主动找来。
灰白：研一学长，零基础。网名“灰白”，取“灰色地带+白光”之意。因看到焲痕社的光轨视频前来尝试，动作别扭但练得认真。第14周因研一课业压力退社。
二、数据模型与计算公式
2.1 技艺计算
技艺 = 10 + Σ（已解锁技能的难度 × 熟练度 ÷ 10）
初始：雷蛇（难度1，熟练度40）= 贡献4，天照（难度1，熟练度40）= 贡献4，基础10 → 技艺18
每次熟练度变化后实时重算

2.4 熟练度规则
天空之境：所有已解锁技熟练度+10
特定演出成功：选定技+15
每周衰减：难度1-3不衰减，难度4衰减2点，难度5衰减3点，最低为0
2.5 知名度获取公式
单技知名度 = 难度系数 × 观赏度系数 × 熟练度系数 × 衰减系数
难度系数 = 难度×6+4
观赏度系数 = 观赏性×3+2
熟练度系数 = 0.5 + 熟练度÷200
衰减系数 = 0.9^使用次数
一次行动知名度 = 所选3个技的单技知名度之和（取整）

七、代码架构
7.1 架构总览
《光轨》采用 “状态-事件-视图”三层架构，核心思想是逻辑与表现分离，事件驱动数据流。通过Godot的Autoload功能实现四个全局单例，各司其职：
单例
角色
职责
DataStore
状态中心
唯一的数据源（Single Source of Truth）。所有游戏运行时状态集中于此，数据变更时发出Signal
GameManager
流程调度
控制周次循环、剧情触发判定、结局检测。持有DataStore引用，读取状态并执行游戏规则
UIManager
表现层
负责所有界面显示。监听DataStore信号，接收GameManager调用
EventManager
事件总线
全局事件调度中心。允许各模块通过事件名通信而不直接互相依赖
引入EventManager的原因：之前的架构中GameManager直接调用UIManager，导致游戏逻辑模块需要知道UI模块的接口细节，耦合度高。引入EventManager后，GameManager只发布事件，UIManager订阅事件自行响应，两者不再直接依赖。
层级规则：
DataStore 完全独立，不持有任何模块引用，仅发出Signal
GameManager 持有DataStore引用（读写状态），需要触发UI时通过EventManager发布事件
UIManager 监听DataStore的Signal和EventManager的事件，自行决定如何响应
EventManager 独立于所有模块，仅作为事件通道存在
7.2 Autoload配置
在Godot项目设置（项目→项目设置→自动加载）中按以下顺序添加：
text
1. EventManager    # 事件总线，最先加载（其他模块订阅事件时需要它已存在）
2. DataStore       # 数据层
3. UIManager       # UI层，订阅DataStore信号
4. GameManager     # 逻辑层，持有DataStore引用
C#中通过 GetNode<T>("/root/单例名") 获取Autoload节点的强类型引用。
7.3 核心模块设计
7.3.1 EventManager —— 全局事件总线
Godot社区推荐的最佳解耦方案。当游戏中有数十个模块需要互相通信时，一个集中的事件总线比让每个节点互相持有引用更清晰、更易维护。
csharp
// EventManager.cs —— 全局事件总线（Autoload单例）
// 设计说明：采用静态泛型方式，避免Godot Signal的字符串依赖和类型转换问题。
// 参考Godot社区最佳实践，使用C#原生泛型事件实现类型安全的事件总线。
public partial class EventManager : Node
{
    // 存储所有事件订阅：事件类型 → 回调函数列表
    // 泛型设计确保每个事件类型都有独立的订阅者列表
    private static readonly Dictionary<Type, List<Delegate>> _subscribers = new();

    // 订阅事件：T为事件数据类型（如DialogueShowEvent、WeekAdvanceEvent等）
    public static void Subscribe<T>(Action<T> callback)
    {
        Type type = typeof(T);
        if (!_subscribers.TryGetValue(type, out var list))
        {
            list = new List<Delegate>();
            _subscribers[type] = list;
        }
        list.Add(callback);
    }

    // 发布事件：携带类型安全的事件数据
    public static void Publish<T>(T evt)
    {
        Type type = typeof(T);
        if (!_subscribers.TryGetValue(type, out var list)) return;
        // ToArray()防止在遍历过程中修改列表导致异常
        foreach (var cb in list.ToArray())
        {
            (cb as Action<T>)?.Invoke(evt);
        }
    }

    // 取消订阅：节点释放时必须调用，防止内存泄漏
    public static void Unsubscribe<T>(Action<T> callback)
    {
        Type type = typeof(T);
        if (_subscribers.TryGetValue(type, out var list))
        {
            list.Remove(callback);
        }
    }
}
为什么用静态泛型类而非Godot Signal？
类型安全：Publish<DialogueShowEvent>(evt) 在编译时即可检查类型，避免Godot Signal传入错误的参数类型导致运行时崩溃
性能：静态泛型调用避免了Godot Signal的字符串查找和Variant装箱/拆箱开销
解耦更彻底：发送方和接收方都不需要继承Node或挂在场景树中，纯C#类也能参与事件通信
代码提示友好：IDE可以对泛型事件提供完整的自动补全
【备选方案】Godot Autoload Signal实现如果偏好使用Godot原生的Signal系统（例如需要与GDScript交互），也可以使用Autoload Signal方式：

        double visualCoeff = visual * 3 + 2;
        double profCoeff = 0.5 + proficiency / 200.0;

// GameManager.cs —— 游戏流程控制（Autoload单例）
public partial class GameManager : Node
{

    public override void _Ready()

    // 开始新游戏

        // 序章结束后进入第1周
    }

    // 玩家选择地点后的处理
    public void OnPlayerAction(string locationId)
    {
        switch (locationId)
        {
            case "yongman_theater": // 咏曼剧场
                // 抽5选2学技逻辑
                _data.BeijingOneCount = 0; // 不影响北京壹号计数
                break;
            case "sky_mirror": // 天空之境
                _data.PracticeAllSkills();
                EventManager.Publish(new ActionResultEvent("反复练习，你找到了正确的发力感觉。"));
                break;
            case "beijing_one": // 北京壹号
                _data.BeijingOneCount++;
                // 知名度获取逻辑
                break;
            case "stage": // 爬台
                _data.StageCount++;
                // 知名度获取逻辑 + 35%概率社团人数+1
                break;
            // ... 其他地点
        }

        // 行动后检查判定触发剧情
        CallDeferred(nameof(CheckConditionalEvents));
    }

    // 推进周数
    public void AdvanceWeek()
    {
        _data.ApplyWeeklyDecay(); // 先衰减
        _data.CurrentWeek++;
        EventManager.Publish(new WeekAdvanceEvent(_data.CurrentWeek));

        if (_data.CurrentWeek > 20)
        {
            CheckEnding();
            return;
        }

        // 触发本周固定剧情（若有）
        TriggerFixedStory(_data.CurrentWeek);
    }

    // 检查所有判定触发剧情
    private void CheckConditionalEvents()
    {
        // 按优先级检查（数字越小优先级越高）：

        // 【优先级1】第一次线上招新
        if (!_data.HasRecruited && _data.Fame >= 30)
        {
            _data.HasRecruited = true;
            TriggerEvent("recruit");
            return;
        }

        // 【优先级2】第一次登台
        if (!_data.HasFirstStage && _data.YiJi >= 25
            && _data.UnlockedSkills.Count >= 3 && _data.HasRecruited)
        {
            _data.HasFirstStage = true;
            TriggerEvent("first_stage");
            return;
        }

        // 【优先级3】第二次爬台（第7周后的第一次爬台）
        if (!_data.HasSecondStage && _data.CurrentWeek >= 7
            && /* 当周行动为爬台 */)
        {
            _data.HasSecondStage = true;
            TriggerEvent("second_stage");
            return;
        }

        // 【优先级4】家虎哥事件
        if (!_data.HasCyberbully && _data.Fame >= 120)
        {
            _data.HasCyberbully = true;
            TriggerEvent("cyberbully");
            return;
        }

        // 【优先级5】网络瓶颈
        if (!_data.HasBottleneck && _data.BeijingOneCount >= 3)
        {
            _data.HasBottleneck = true;
            TriggerEvent("bottleneck");
            return;
        }

        // 【优先级6】场地临时取消
        if (!_data.HasVenueCancel && _data.StageCount >= 2)
        {
            _data.HasVenueCancel = true;
            _data.VenueCancelWeek = _data.CurrentWeek;
            TriggerEvent("venue_cancel");
            return;
        }

        // 【优先级7】林若进线（网暴事件后前往咏曼/天空之境）
        if (!_data.IsLinRuoRoute && _data.HasCyberbully
            && _data.YiJi >= 45 /* && 当周前往咏曼或天空之境 */)
        {
            TriggerEvent("linruo_route_entry");
            return;
        }

        // 【优先级8】宋柯进线（网暴后前往回声 + 知名度≥300）
        if (!_data.IsSongKeRoute && _data.HasCyberbully
            && _data.IsEchoUnlocked && _data.Fame >= 300
            /* && 当周前往回声 */)
        {
            TriggerEvent("songke_route_entry");
            return;
        }

        // 【优先级9】叶子进线（第19周 + 技艺≥55）
        if (!_data.IsYeziRoute && _data.CurrentWeek >= 19 && _data.YiJi >= 55)
        {
            TriggerEvent("yezi_route_entry");
            return;
        }
    }

    // 触发指定事件（通过Dialogue Manager播放对应.dialogue文件）
    private void TriggerEvent(string eventId)
    {
        EventManager.Publish(new DialogueShowEvent("system", eventId, ""));
    }

    // 触发固定周目剧情
    private void TriggerFixedStory(int week)
    {
        // 根据week和当前进线状态，播放对应的.dialogue文件
        string storyId = $"week{week}";
        if (_data.IsLinRuoRoute && week >= 16) storyId += "_linruo";
        else if (_data.IsSongKeRoute && week >= 17) storyId += "_songke";
        EventManager.Publish(new DialogueShowEvent("system", storyId, ""));
    }

    // 结局判定
    public void CheckEnding()
    {
        // 1. 厄介结局（过激应援≥2）
        if (_data.AggressiveCount >= 2)
        {
            EventManager.Publish(new EndingTriggerEvent("akugeki"));
            return;
        }

        // 2. 社恐结局（三线未进 且 知名度≥500）
        if (!_data.IsLinRuoRoute && !_data.IsSongKeRoute && !_data.IsYeziRoute
            && _data.Fame >= 500)
        {
            EventManager.Publish(new EndingTriggerEvent("shakou"));
            return;
        }

        // 3. 社团HE（知名度≥500 且 社团人数≥5）
        bool isClubHE = _data.Fame >= 500 && _data.MemberCount >= 5;

        // 4. 在社团HE基础上判定个人结局
        if (isClubHE)
        {
            if (_data.IsLinRuoRoute && _data.YiJi >= 75)
                EventManager.Publish(new EndingTriggerEvent("linruo_light_ring"));
            else if (_data.IsSongKeRoute && _data.Fame >= 600)
                EventManager.Publish(new EndingTriggerEvent("songke_light_shadow"));
            else if (_data.IsYeziRoute)
                EventManager.Publish(new EndingTriggerEvent("yezi_outside_light"));
            else
                EventManager.Publish(new EndingTriggerEvent("club_he"));
        }
        else
        {
            EventManager.Publish(new EndingTriggerEvent("club_be"));
        }
    }
}

7.4 数据流示意
以下以“玩家在天空之境练习”为例，展示数据如何在整个架构中流动：
text
1. 玩家点击“天空之境”按钮
   ↓
2. Button.pressed 信号 → GameManager.OnPlayerAction("sky_mirror")
   ↓
3. GameManager → DataStore.PracticeAllSkills()
   ├── 所有技能熟练度+10
   ├── RecalculateYiJi() 重算技艺面板值
   └── DataStore发出 SkillChangedEvent
   ↓
4. GameManager → EventManager.Publish(new ActionResultEvent("反复练习，你找到了正确的发力感觉。"))
   ↓
5. UIManager.OnActionResult() 收到事件 → 显示反馈文本
   UIManager.OnSkillChanged() 收到Signal → 刷新属性面板
   ↓
6. GameManager.CallDeferred(nameof(CheckConditionalEvents))
   └── 检查是否有判定触发剧情需要触发（如技艺达到25触发第一次登台）
关键设计点：
CallDeferred的使用：CheckConditionalEvents 使用 CallDeferred 延迟到下一帧调用。这是因为当前帧中DataStore的状态更新可能尚未完全传播到所有监听者，延迟调用可以确保所有Signal已被处理完毕后再进行条件判定，避免时序问题。
事件与Signal的配合：DataStore使用Godot原生Signal发出状态变化通知（与Godot编辑器集成好），GameManager与UIManager之间使用静态EventBus通信（更解耦）。两者各司其职。

7.5.2 EasySave —— 存档管理
Asset Library 地址：https://godotengine.org/asset-library/asset/4841
EasySave 是专为 Godot 4.x C# 设计的轻量级存档插件，零依赖，基于Godot原生Resource序列化机制。
为什么推荐它？
零依赖：不依赖任何第三方库，纯Godot原生API实现
多槽管理：支持多存档槽的保存/读取/删除
类型安全：提供泛型API，编译时即可检查类型错误
跨场景传递：存档数据可以在不同场景间安全传递
信号通知：保存/加载完成时发出通知，UI可以响应
安装步骤：
在 Godot Asset Library 中搜索 "EasySave"，下载并安装
在项目设置 → Plugins 中启用 EasySave
在C#脚本中添加：using EasySave;
在DataStore中集成存档功能：
csharp
// DataStore中定义存档数据结构
[GlobalClass]
public partial class SaveData : Resource
{
    [Export] public int YiJi;
    [Export] public int Fame;
    [Export] public int MemberCount;
    [Export] public int CurrentWeek;
    [Export] public Godot.Collections.Array<SkillSaveData> UnlockedSkills;
    // ... 其他需要保存的字段
}

// 序列化当前状态为SaveData
public SaveData ToSaveData()
{
    var data = new SaveData();
    data.YiJi = this.YiJi;
    data.Fame = this.Fame;
    // ... 复制所有字段
    return data;
}

// 从SaveData恢复状态
public void FromSaveData(SaveData data)
{
    this.YiJi = data.YiJi;
    this.Fame = data.Fame;
    // ... 恢复所有字段
    RecalculateYiJi();
}
备选方案：Godot原生Resource序列化
如果不想引入额外插件，Godot自带的Resource系统也完全可以实现存档功能。创建一个继承自Resource的SaveData类，使用ResourceSaver.Save()和ResourceLoader.Load<T>()读写.tres或.res文件即可。
csharp
// 存档路径（user:// 指向系统用户数据目录，打包后仍然可用）
private string SavePath = "user://save.tres";

// 保存
public void SaveGame()
{
    var saveData = ToSaveData();
    ResourceSaver.Save(saveData, SavePath);
}

// 加载
public bool LoadGame()
{
    if (!FileAccess.FileExists(SavePath)) return false;
    var saveData = ResourceLoader.Load<SaveData>(SavePath);
    if (saveData == null) return false;
    FromSaveData(saveData);
    return true;
}

7.7 推荐开发顺序
基于以上架构，推荐按以下顺序进行开发：
搭建Autoload四件套：先写EventManager和DataStore（纯数据、无UI依赖），再写UIManager和GameManager的骨架（_Ready中获取引用和订阅事件）。这一阶段所有模块可单独编译测试。
接入Dialogue Manager：在Asset Library中搜索“Dialogue Manager”安装；按插件文档完成初始化；把序章剧情写成一个.dialogue文件；跑通“启动→序章→进入地图”的整条流程。
搭建主地图场景：放置地点图标按钮；连接信号到GameManager的OnPlayerAction方法；实现简单反馈文本显示。
实现周次循环：编写AdvanceWeek()方法；串联“行动反馈→固定剧情→判定触发→衰减→下一周”的完整流程；先用第1周的简单剧情验证循环。
接入EasySave（或使用原生Resource序列化）：实现ToSaveData()和FromSaveData()方法；加入主菜单的“读取存档”按钮逻辑。
开发核心数值系统：技能池随机抽取、学技成功率、知名度计算公式、熟练度衰减规则——全部在DataStore中以纯计算方法实现。
填充全部剧情：逐个编写每段剧情的.dialogue文件；利用Dialogue Manager的条件跳转实现数值门槛判定。
实现结局判定：CheckEnding()方法按优先级依次检查条件；UIManager通过EventManager订阅EndingTriggerEvent，收到事件后播放对应结局演出。

7.9 关键开发注意事项
技艺需实时计算：每次熟练度变化后调用RecalculateYiJi()更新面板值。技艺不是存储值，而是计算值，这样避免了存储值与实际技能数据不一致的bug。
知名度无上限：UI需适配大数值显示（可能超过1000）。
学院路解锁与知名度≥30的第一次招新事件绑定，不可直接通过周数硬编码解锁。第3周只是预期的触发时间，实际触发取决于玩家的知名度积累速度。
回声Livehouse图标根据第6周选项结果动态显示/隐藏。这要求在DataStore中持久记录第6周的选项选择。
过激应援次数达2次立即进入厄介结局，不等待第20周。判定逻辑在AdvanceWeek()中每次行动后检查。
所有选项的进线状态和数值增益需在DataStore中持久记录，供结局判定使用。建议使用Dictionary存储。
技能每周衰减仅针对难度4-5技能，执行时机在周数推进前（先衰减再+1周）。
网络瓶颈和场地临时取消通过累计计数器触发。计数器在对应地点行动后递增，并在CheckConditionalEvents()中检查阈值。
社恐结局的B站私信及短视频为结局演出内容，需在结局系统中实现对应叙事流程。
所有地点的简短反馈为固定文本，仅需从配置表中按locationId读取对应字符串，无需每次随机生成。
EventManager订阅管理：任何订阅了EventManager事件的节点，必须在_ExitTree()中调用Unsubscribe取消订阅。忘记取消订阅会导致：① 节点已被销毁但回调仍然存在，触发事件时抛出空引用异常；② 内存泄漏——已销毁节点无法被GC回收。这是事件总线架构中最常见的bug来源。
CallDeferred的使用场景：当需要在当前帧的所有状态更新完成后再执行逻辑时（如CheckConditionalEvents、切换场景），使用CallDeferred延迟到下一帧，避免时序问题。
